# Покрытие OpenAPI 3.1

Typed-endpoint генерирует документ OpenAPI `3.1.0` из скомпилированных
маршрутов. Это оценка возможностей генератора, а не доля всех правил стандарта
или совместимость с произвольным входным OpenAPI-документом. За основу взяты
фиксированные поля [OpenAPI Object](https://spec.openapis.org/oas/v3.1.0.html#openapi-object)
и [Operation Object](https://spec.openapis.org/oas/v3.1.0.html#operation-object)
из спецификации OpenAPI 3.1.0.

## Как посчитано

У корневого объекта 10 фиксированных полей, у операции — 12. Каждое поле
получает 1 балл, если его основная семантика доступна через типизированный API;
0,5 балла, если доступна только часть вариантов или вложенных возможностей;
0 баллов, если поле генератор не выводит. Поля `x-*` и вложенные поля не входят
в знаменатель. Ручная правка готового JSON и `Json_schema.Unsafe` не считаются
поддержкой типизированного API.

Сейчас полностью поддержано 6 полей, частично — 9, отсутствуют 7. По этой
методике покрытие составляет `(6 + 9 × 0,5) / 22 = 47,7 %`, то есть
**примерно 48 %**. Без половинных баллов это 27 % полностью поддержанных полей
или 68 % полей с хотя бы частичной поддержкой. Число 48 % — ориентир для
сравнения изменений библиотеки, а не официальный процент OpenAPI: глубина
вложенных объектов у полей сильно различается.

## Корневой OpenAPI Object: 1 полностью, 5 частично, 4 отсутствуют

- `openapi` — полностью: генератор указывает версию `3.1.0`.
- `info` — частично: есть `title`, `version`, `description`; нет `summary`,
  `termsOfService`, `contact` и `license`.
- `jsonSchemaDialect` — отсутствует: нельзя указать иной диалект схем по
  умолчанию.
- `servers` — частично: есть URL и описание; нет `variables`.
- `paths` — частично: создаются пути с типизированными capture и операции
  GET, POST, PUT, DELETE, PATCH. Одинаковые path-параметры нескольких операций
  автоматически поднимаются в Path Item. Нет HEAD, OPTIONS, TRACE и явного
  объявления общих полей Path Item, например `servers` и `$ref`.
- `webhooks` — отсутствует.
- `components` — частично: создаются `schemas` и `securitySchemes`.
  Вложенные копии зарегистрированных объектных моделей переиспользуются через
  `$ref`. Response Objects остаются inline; `components.responses` и другие
  виды компонентов не объявляются.
- `security` — отсутствует на уровне документа; требования задаются у
  отдельных операций.
- `tags` — частично: выводятся имя и описание тега группы; нет
  `externalDocs` и самостоятельного описания тега.
- `externalDocs` — отсутствует.

## Operation Object: 5 полностью, 4 частично, 3 отсутствуют

- `tags` — полностью: операция получает список тегов из группы и собственного
  объявления.
- `summary` — полностью.
- `description` — полностью.
- `externalDocs` — отсутствует.
- `operationId` — полностью: значение выводится и проверяется на уникальность
  при компиляции.
- `parameters` — частично: есть path, query и header со схемой, обязательностью
  и описанием; reserved headers `Accept`, `Content-Type` и `Authorization`
  отклоняются. `Query.csv`/`Query.repeated` задают `style: form` и `explode`
  для query-массивов. Нет cookie, остальных стилей, `content` и примеров.
- `requestBody` — частично: есть JSON, обычный текст и бинарное тело с
  `required=true`. Для JSON `Request.json ~media_types` публикует несколько
  конкретных media types с одним codec и схемой; по умолчанию — `application/json`.
  Нет альтернативных форматов с разными codecs, форм, multipart,
  необязательного body и примеров.
- `responses` — частично: есть конкретные финальные HTTP-статусы 200--599,
  пустое тело, JSON, обычный текст и заголовки; 204/205/304 требуют пустого тела.
  Нет `default` и диапазонов статусов, `links`,
  примеров и произвольных media types.
- `callbacks` — отсутствует.
- `deprecated` — полностью.
- `security` — частично: есть требования для операции и схемы API key,
  HTTP Bearer, OAuth2 implicit. Нет других HTTP-схем, OAuth2 flows,
  OpenID Connect и mutual TLS.
- `servers` — отсутствует на уровне операции.

## Как читать результат

Поддержка поля `components` не означает поддержку всего JSON Schema 2020-12:
`Json_schema` и PPX дают типизированное подмножество, включая DTO, ограничения,
`$ref` и `$defs`. `Json_schema.Unsafe` позволяет импортировать сторонний
фрагмент схемы, но его корректность и соответствие OCaml-типу остаются
ответственностью вызывающего кода.

Ручной `Json_schema` поддерживает строковые patterns и content encoding,
строгие числовые границы и кратность, префиксы массивов и `contains` с границами
совпадений, enum/const для составных значений, ограничения ключей и зависимостей
объекта, логические и условные композиции. Явный `discriminator` описывает
объектные композиции без генерации codec. `contramap` связывает существующую
схему с абстрактным типом через его представление. Этот набор не добавляет
новых PPX-аннотаций или автоматической runtime-валидации.

Для обычного JSON API с типизированными маршрутами, параметрами, ответами и
авторизацией генератор покрывает основной сценарий. Если контракту нужны,
например, multipart, callbacks, webhooks или глобальные security requirements,
готовый документ не выразит их через текущую декларацию endpoint.
