# ADR 0001: Отдельные контракты маршрутов и чистая сборка OpenAPI

- **Статус:** не принято.
- **Дата:** 2026-10-08.
- **Область:** экспериментальная ветка `experimental`; API ветки `master` этим
  документом не меняется.

## Контекст

В `master` описание маршрута заканчивается оператором `==>`, который сразу
связывает его с обработчиком. OpenAPI строится из скомпилированного графа
runtime-маршрутов. Для получения этого графа нужно инстанцировать `Make (B)`
и передать модули зависимостей приложения, даже если HTTP-сервер не запускается.
Это мотивировало поиск объявления, из которого можно получить OpenAPI до
выбора backend, обработчиков и database.

Две реализации в ветке `experimental` исследовали разные границы такого
объявления. Они зафиксированы коммитами `196136e` и `c20b1e3`. Оба коммита
остаются экспериментом: ни один из их публичных API не принят для `master`.

## Первая реализация: дополнительный контракт и OCaml-клиент

Коммит `196136e` добавил `Typed_endpoint.Experimental.Contract` как
необязательную альтернативу inline DSL. Отдельный контракт описывал path,
query, headers, request и типизированные варианты response. Внутри
`Make (B)` оператор `==>` привязывал к нему обработчик с теми же позиционными
аргументами. Обычная запись `returns ... ==> handler` оставалась основной.

Эксперимент также добавил клиентскую часть: двунаправленные кодеки для
клиентского контракта, независимое от транспорта ядро OCaml-клиента,
`typed-endpoint-fetch` и браузерный пример Petstore. Серверный контракт без
клиентских кодеков оставался пригодным для сервера, но не становился
клиентским. Клиент возвращал типизированные объявленные статусы и отдельно
различал сетевую ошибку, неожиданный статус и невалидный ответ.

Отдельный endpoint можно было объявить без backend, но группа маршрутов и
компиляция полного OpenAPI по-прежнему принадлежали runtime API `Make (B)`.
Следовательно, эта версия не решала задачу экспорта всего документа без
создания backend и зависимостей приложения. Совместное развитие контрактов и
сетевого клиента также заметно увеличило поверхность эксперимента.

## Вторая реализация: контракт как основной API

Коммит `c20b1e3` сделал `Typed_endpoint.Contract` основным способом объявления
маршрута. `Contract.Group.make` собирает backend-независимый граф с prefix,
tags, security, policy responses и decode-error policy. `Contract.compile`
проверяет этот граф и строит OpenAPI без обработчиков, backend и database.
`Make (B).bind` и `bind_with_context` отдельно связывают те же объявления с
runtime-обработчиками. Типовая связь path/query/header/body и объявленных
response cases с аргументами обработчика сохранена. Petstore использует
`Api_contract` и отдельный исполняемый экспортёр OpenAPI.

В этой итерации удалены OCaml-клиент, Fetch-адаптер и клиентские DTO первой
реализации. Контракты Petstore объявляются вне `Make`, а контроллеры обходятся
без `.mli`, чтобы типы обработчиков выводились из привязки. Ряд объявлений
оформлен как функции `unit -> Contract.t`: это сохраняет нужную полиморфность
стадий DSL при ограничении обобщения значений OCaml.

Главный оставшийся разрыв — состав групп. Например, Petstore перечисляет
endpoint-контракты в `Api_contract.pet_oauth_group`, а привязанные маршруты
второй раз в `Pet_controller.Make.groups`. Общие метаданные частично вынесены
в `Api_metadata`, но единый список участников группы отсутствует. Компилятор
типов проверяет каждую привязку, однако не доказывает, что OpenAPI и runtime
содержат одинаковый набор маршрутов. При добавлении или удалении endpoint
списки могут разойтись. Это ограничивает утверждение о едином источнике
данных: декларация **отдельного маршрута** общая, композиция групп пока нет.

## Сравнение с другими подходами

| Подход | Откуда берётся OpenAPI | Что требуется для генерации |
| --- | --- | --- |
| Spring Boot + springdoc-openapi | Из зарегистрированных Spring-маршрутов и аннотаций приложения. | Штатный Maven-плагин запускает приложение, запрашивает локальный `/v3/api-docs` и останавливает его. Поднимается Spring context; singleton beans по умолчанию создаются при его инициализации. Значит, без специальной конфигурации могут потребоваться реальные зависимости приложения. |
| ASP.NET Core, встроенный OpenAPI | Из описаний endpoint, зарегистрированных приложением; документ можно отдать по HTTP или получить при сборке. | Генерация при сборке запускает entrypoint приложения с mock server. HTTP-порт не нужен, но startup, регистрация DI и чтение конфигурации выполняются; для внешних ресурсов могут понадобиться условные ветви startup. |
| FastAPI | Из дерева зарегистрированных маршрутов `app.routes`; `app.openapi()` вызывает генерацию схемы. | HTTP-сервер для вызова `app.openapi()` не нужен, но объект приложения и регистрация роутеров, включая ссылки на обработчики, уже должны быть созданы. |
| Tapir | Из самостоятельных значений описания endpoint через `OpenAPIDocsInterpreter().toOpenAPI(...)`. | Ни серверный интерпретатор, ни server logic для генерации не нужны; обработчики привязываются отдельно. Это наиболее близкая модель к экспериментальному `Contract`. |

Spring и ASP.NET Core показывают, что «генерация во время сборки» не
обязательно означает независимость от startup и DI. FastAPI отделяет вызов
генератора от HTTP-сервера, но берёт маршруты из уже собранного приложения.
Tapir действительно интерпретирует отдельные описания endpoint. Ни один из
этих примеров сам по себе не решает вопрос гарантированного совпадения двух
независимо составленных списков групп в `typed-endpoint`.

## Итог и условия повторного рассмотрения

**Решение не принято.** Документ фиксирует результаты эксперимента, а не
предлагает слияние `experimental` в `master`. Текущий API `master` и его
roadmap остаются действующими. Прежде чем предлагать контракт как основной
API, нужно обеспечить одну композицию группы для документа и runtime либо
явную проверку равенства их наборов маршрутов; сохранить типовую связь
объявления и обработчика; оценить цену миграции; отдельно решить, входит ли
OCaml-клиент в область изменения. Чистая сборка OpenAPI во второй реализации
подтверждает полезность разделения декларации и обработчика, но не закрывает
вопрос архитектуры групп.
