# ADR 0002: OpenAPI-first генератор и выбор версии экспорта

- **Статус:** принят; первый этап реализован с ограничениями.
- **Дата:** 2026-10-23.
- **Область:** отдельный генератор DTO и серверного HTTP-слоя, расширение
  decode-error policy и дополнительный API экспорта. Существующий
  `Compiled.openapi` сохраняет прежний формат 3.1.0.

## Контекст

Аналитический контракт может быть написан в OpenAPI до появления серверной
реализации. В таком процессе нужны способы перенести его в типизированный
HTTP-слой и проверить соответствие реализации исходному документу.

[ADR 0001](0001-contracts-and-openapi.md) рассматривает самостоятельный
OCaml-контракт, из которого получают runtime и OpenAPI. Здесь направление
обратное: исходником служит OpenAPI, а OCaml-декларации создаёт генератор.
Отдельный публичный `Contract` API не является предварительным условием:
серверные обёртки можно генерировать поверх существующего DSL.

Генератор не восстанавливает доменные OCaml-типы из JSON Schema. Он создаёт
транспортные DTO, а приложение явно преобразует их в `Domain` и обратно.
Так сохраняется направление зависимостей Petstore: controller → application
service → repository port.

## Альтернатива: сравнение двух OpenAPI

Можно сохранить рукописные DTO и маршруты, экспортировать OpenAPI реализации
и сравнивать его с аналитическим контрактом. Этот подход требует меньше
генерации, но структура HTTP API описывается дважды.

Сравнение должно учитывать структуру OpenAPI: порядок полей, inline-схемы и
`$ref`, наследование параметров и документирующие метаданные. Проверки только
breaking changes недостаточно: совместимое изменение тоже может отклоняться
от согласованного контракта. Например, дополнительная операция может быть
совместима с клиентом, но отсутствовать в требованиях. Возможный инструмент
такой проверки — `oasdiff diff` с явно выбранными правилами сравнения.

Сравнение документов остаётся полезным и при генерации: оно проверяет
сохранение деклараций. Фактический HTTP-ответ нужно проверять отдельно по
исходному контракту. Совпадение двух документов само по себе не доказывает
корректность codecs, guards или прикладного поведения.

## Вход и декларативное именование схем

Вход генератора — **один или несколько дереференсированных JSON OpenAPI
3.0.3 или 3.2.1**. Разрешение исходных ссылок выполняется до генерации.
Каждому файлу можно явно назначить группу; общий запуск строит единый граф
DTO и проверяет идентичность схем между файлами. Анонимные схемы имеют
локальную идентичность в пределах источника. Поддержка YAML и
самостоятельного дереференса в это предложение не входит.

Имена полей метаданных не зашиваются в генератор. Опциональная декларативная
конфигурация задаёт извлечение имени типа и, отдельно, идентичности схемы:

- `type_name` выбирает строку, из которой получается основа имени типа;
- `schema_identity` выбирает устойчивый строковый идентификатор для
  переиспользования DTO между операциями и группами;
- `select` — JSON Pointer относительно обрабатываемого объекта схемы;
- `transform` задаёт преобразование выбранной строки. Без него строка
  используется целиком; `json_pointer_last_segment` извлекает и декодирует
  последний сегмент JSON Pointer, в том числе записанного с префиксом `#`.

Конфигурация показывает, как использовать метаданные происхождения,
сохранённые после дереференса:

```json
{
  "naming": {
    "type_name": {
      "select": "/sourceRefs/0",
      "transform": "json_pointer_last_segment"
    },
    "schema_identity": {
      "select": "/sourceRefs/0"
    }
  }
}
```

Для такой конфигурации входная схема может выглядеть так:

```json
{
  "sourceRefs": ["#/components/schemas/Pet"],
  "type": "object",
  "properties": {
    "name": { "type": "string" }
  },
  "required": ["name"]
}
```

Выбранный идентификатор — `#/components/schemas/Pet`, основа имени — `Pet`,
результат нормализации — `Dto.Pet.t`. Для другого поля достаточно изменить
`select`; если оно уже содержит готовое имя, преобразование не требуется.
Настройки извлечения имени и идентичности независимы: совпадение имён не
означает, что схемы представляют один тип.

Нестандартные служебные поля подготовленного входа не становятся полями DTO
или keywords схемы в публичном экспорте. Стандартные поля OpenAPI сохраняют
свою семантику независимо от их использования при именовании. Имена типов
нормализуются до допустимых OCaml-идентификаторов; wire-имена сохраняются
в codecs.

Повторные появления одного извлечённого идентификатора используют общий
DTO, в том числе между группами. При этом генератор проверяет согласованность
раскрытых определений: несовместимые схемы с одним идентификатором нельзя
молча объединять. Разные идентификаторы не становятся одним типом только
из-за совпадения структуры.

Если соответствующая настройка не задана или выбранное поле отсутствует,
идентификатор или основа имени образуются из HTTP-метода, пути операции
и места использования схемы. Для вложенных схем учитываются имена свойств
и позиции в коллекциях. Некорректная конфигурация, выбранное значение другого
типа или ошибка преобразования требуют диагностики, а не молчаливого fallback.

| Место использования без извлечённого имени | Основа имени типа |
| --- | --- |
| Body запроса `POST /pets` | `Dto.Post_pets_request_body.t` |
| Ответ 200 на `GET /pets/{pet_id}` | `Dto.Get_pets_by_pet_id_response_200.t` |
| Элемент массива этого ответа | `Dto.Get_pets_by_pet_id_response_200_items.t` |
| Свойство `address` в body `POST /users` | `Dto.Post_users_request_body_address.t` |

Коллизии имён после нормализации разрешаются стабильным суффиксом от полного
идентификатора схемы. Номер обхода использовать нельзя: перестановка полей
JSON не должна менять сгенерированные имена. Суффикс состоит из первых восьми hex-символов digest
идентификатора и удлиняется при совпадении префиксов. Регистр и разделители
нормализуются; правила покрыты regression tests.

## DTO, операции и серверные обёртки

Генератор создаёт DTO, JSON codecs и связанные с типами схемы, типы запросов
и ответов операций, обязательные записи обработчиков и сборку маршрутов.
Публичные интерфейсы создаются в `.mli`. Для DTO используются
`ppx_deriving_yojson`, `typed-endpoint-ppx` и общие wire-аннотации там, где
их семантика соответствует исходному контракту. Особые wire-представления
нельзя заменять похожими, но несовместимыми схемами или codecs.

Операции распределяются по группам по первому статическому сегменту пути:
`/pets/{pet_id}` → `Pets`, `/users/{user_id}` → `Users`. Это группировка
сгенерированного кода; она не добавляет prefix и не меняет HTTP-пути.
DTO имеют общее пространство имён на всё приложение, поскольку один тип
может использоваться в нескольких группах.

Обработчик получает типизированный request record и возвращает вариант
объявленного ответа с соответствующим payload и response headers. Все
операции группы представлены обязательными полями записи обработчиков:
после добавления операции компилятор требует её реализацию. Список runtime
маршрутов отдельно вручную не перечисляется.

Серверные обёртки специализируются через `Make (B)` и используют
`Backend.S.io`. Они создают обычные декларации текущего DSL, разрешают
контекст, декодируют запрос, вызывают обработчик и переводят его результат
в типизированный `respond`. Лимит чтения body и порядок относительно
разрешения контекста сохраняют правила ядра.

Сокращённый пример привязки; полные записи обработчиков и мапперов ошибок
приведены в [рабочем примере](../../examples/openapi/integration_test.ml):

```ocaml
open! Base

module Server = Generated_api.Server.Make (B)
module Endpoint = Server.Endpoint

let groups =
  Server.Pets.groups ~context:pets_context ~decode_errors:pets_decode_errors
    pets_handlers
  @ Server.Animals.groups ~context:animals_context
      ~decode_errors:animals_decode_errors animals_handlers
;;

let compiled = Endpoint.compile groups
```

Группы используют один backend, но могут получать разные типы контекста.
Database и конкретные сервисы выбираются в composition root. Контроллеры
передают сервисам доменные значения и явно выбирают объявленный HTTP-ответ.
Маппинги DTO ↔ Domain остаются рукописными; преобразование входного DTO
может возвращать `Result` при нарушении доменного инварианта.

Генерируемые файлы отделяются от рукописных и могут полностью пересоздаваться.
Records запросов, варианты ответов и записи обработчиков относятся только
к необязательному генерируемому фасаду. Они не заменяют curried arguments
и цепочку responses в существующем рукописном DSL.

## Предполагаемые схемы и границы runtime

В первой версии поддерживаются объекты, скаляры, строковые enums, массивы, словари,
optional и nullable, а также `oneOf` с discriminator и совместимые объектные
`allOf`. Произвольные `anyOf`, неоднозначные варианты и непредставимые
пересечения не считаются автоматически поддержанными.

Для OpenAPI 3.0.3 нужно соблюдать его семантику: необязательность поля задаётся через
`required`, а допустимость `null` — через `nullable: true` с учётом остальных
ограничений схемы. Отсутствие поля и явный `null` нельзя смешивать там, где
они различаются по контракту. Обычный `option` подходит не для всех таких
представлений; это особенно существенно для PATCH DTO.

Ограничения вроде `minimum`, `minLength` и `pattern` сохраняются в схеме,
но автоматическая runtime-валидация JSON Schema не добавляется. Как и в
текущем ядре, codecs проверяют wire shape, а дополнительные проверки
выполняет приложение. Границы гарантий описаны в
[проверке соответствия контракту](../contract_conformance.md).

Для автоматических decode errors с собственными DTO предусматриваются
типизированные рукописные мапперы `Decode_error → DTO`. Генератор не может
вывести значения произвольных полей ошибки из одной схемы. Для разных
payload по статусам 400/413/415 используется `Decode_error_response.by_status`
с отдельными типизированными cases для каждого статуса. Runtime-статусы, wire shape и
публикуемые ответы должны оставаться согласованными.

Подключение авторизации остаётся открытым вопросом возможного развития.
`security` описывает требования, но не реализацию проверки токена или
прав доступа. Генератор не должен молча превращать защищённую операцию
в публичную. Одна группа сгенерированного кода при необходимости может
собирать несколько runtime-групп с разными guards.

## Выбор версии экспорта

Для входа 3.2.1 применяются JSON Schema 2020-12: null unions, строковый
`const`, числовые exclusive bounds и boolean schema `true`. Диалект
проверяется явно; неподдерживаемые keywords и HTTP-возможности 3.2.1
отклоняются. Детали и пример нескольких файлов — в [руководстве](../openapi_first.md).

Версия входного контракта и версия экспортируемого документа независимы.
Поддерживается явный выбор **OpenAPI 3.0.3, 3.1.0 или 3.2.1** при экспорте как для
генерируемых, так и для рукописных маршрутов.

Существующий `Compiled.openapi` без новых настроек сохраняет экспорт 3.1.0.
`Openapi.Config.version` по-прежнему означает `info.version`, то есть версию
прикладного API. Выбор версии спецификации должен быть отдельным параметром,
например `spec_version`.

Для выбора целевой версии добавлен `Compiled.export_openapi ~spec_version`
с результатом `(Yojson.Safe.t, Openapi.Export_error.t list) Result.t`.
`Openapi.Spec_version.t` содержит `V3_0_3`, `V3_1_0` и `V3_2_1`. Это позволяет сообщать
о непредставимых конструкциях без изменения контракта существующей функции.

Экспорт 3.0.3 требует преобразования схем, а не замены строки `openapi`:

- допустимость `null` выражается средствами 3.0.3 с сохранением ограничений;
- числовые exclusive bounds переводятся в представление целевой версии;
- ссылки и компоненты учитывают ограничения Reference Object в 3.0.3;
- keywords и ресурсные области JSON Schema преобразуются только при
  сохранении их смысла.

Если эквивалентное представление не поддержано, экспорт возвращает ошибку
с путём проблемного элемента и причиной. Удалять ограничения или расширять
множество допустимых значений молча нельзя. Поддержка 3.0.3 не означает
возможность преобразовать любую схему текущего `Json_schema`.

При сравнении входного документа 3.0.3 с экспортом другой версии сначала
нужно согласовать диалекты и правила сравнения. Различие представлений
nullable или ссылок само по себе не является расхождением HTTP-контракта.

## Границы первого этапа и дальнейшее развитие

Генератор и CLI находятся в отдельном пакете `typed-endpoint-openapi`.
Результат — фиксированные модули `Support`, `Dto`, `Operations`, `Server`
с `.ml/.mli`. Библиотечная функция генерации чистая, CLI записывает файлы
после успешной проверки входа. Примеры используют правило Dune с
`(mode (promote (until-clean)))`: generated-файлы доступны в отдельной папке
`generated/` для IDE, удаляются при `dune clean` и не хранятся в Git.

V1 принимает конкретные финальные статусы, обязательный JSON request body,
JSON/пустые ответы, scalar path/query/header и query-массивы `form`.
Оставшиеся ссылки, проекции `readOnly`/`writeOnly`, optional request body,
альтернативные body-codecs, default/range responses и неподдерживаемые
композиции отклоняются с JSON Pointer и причиной. Корневые пути и пути без
статического сегмента попадают в группу `Default`.

Авторизация остаётся возможным развитием: эффективная непустая `security`
сейчас вызывает ошибку генерации, а явное `security: []` учитывается.
Достижимые автоматические 400/413/415 должны присутствовать в исходном
контракте; генератор требует для них ручные мапперы и не добавляет статусы
молча. JSON Schema defaults сохраняются как аннотации и не подставляются
в отсутствующие поля.

Проверки включают именование, порядок JSON, коллизии и общие DTO; literal
wire shape optional/nullable и композиций; фактические статусы, headers,
query-массивы и decode errors; compile-fail для отсутствующего обработчика
и неверного payload. Экспорт проверяется отдельно для всех версий,
локальных определений, nullable, числовых границ, opaque literals и ошибок
непредставимых схем. Прежний экспорт 3.1.0 остаётся неизменным.

Точные команды, пример конфигурации и ограничения приведены в
[руководстве](../openapi_first.md).
