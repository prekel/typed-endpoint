# Проверка соответствия контракту

Генерация OpenAPI, нормализация и поведение HTTP проверяются независимо.
Типизированная декларация связывает codecs и schemas, но сама по себе не
доказывает, что любой пользовательский codec соблюдает все ограничения схемы.

| Уровень | Проверяемое свойство | Ответственность |
| --- | --- | --- |
| Генерация | Типы, wire-аннотации и явно объявленные ограничения отражены в схеме | PPX и генератор |
| Нормализация | Схемы до и после преобразования принимают одинаковые значения; описания ответов сохраняются | Нормализатор |
| Runtime | Статус, заголовки, представление и тело соответствуют операции OpenAPI | Codecs, прикладная валидация и сервер |

## Декларативные ограничения

`[@jsonschema.*]` описывают контракт. Они не добавляют JSON Schema-валидатор
в `ppx_deriving_yojson` или HTTP runtime. Например:

```ocaml
type t = { count : int [@jsonschema.minimum 0] }
[@@deriving yojson, jsonschema]
```

Декодер этого DTO принимает `{"count": -1}`, хотя схема его отклоняет.
Приложение должно проверить ограничение в codec или после декодирования,
если отрицательные значения требуется отклонять в runtime. То же относится
к ограничениям длины, коллекций и формату; интерпретация `format` также
зависит от политики выбранного валидатора. Автоматическая runtime-валидация
JSON Schema не входит в текущий DSL.

Общие Yojson-аннотации имеют другую роль: `[@key]`, `[@name]`, `[@encoding]`
и `[@default]` влияют на wire shape codec и учитываются схемой. Обычный
`option` допускает `null`, но не добавляет `default` и не снимает обязательность
record field. Явный `[@default None]` делает поле необязательным и публикует
`default: null`.

Бизнес-валидация может быть строже схемы DTO. Её отказ с объявленным
HTTP-ответом сам по себе не является нарушением схемы входных данных.

## Состав тестов

`make test` запускает существующие regression tests и дополнительные проверки
в `test/conformance/`:

- **Генерация:** PPX fixtures проверяют wire-имена, nullable/required/default,
  форматы, строковое кодирование целых и ограничения. QCheck меняет границы
  чисел и длины коллекций и проверяет их отражение в схеме.
- **Сериализация:** значения, удовлетворяющие объявленным ограничениям,
  сериализуются, проходят валидацию схемы и codec round-trip. Отдельный
  regression test сохраняет пример расхождения декларативного `minimum`
  и независимого Yojson-декодера.
- **Нормализация:** независимый тестовый resolver восстанавливает операции
  и именованные схемы. QCheck сравнивает результаты валидации до и после
  преобразования, включая известные допустимые и недопустимые значения.
  Проверяются inline-ответы, сохранение имён DTO, наследование path-параметров,
  приоритет параметров операции, удаление повторяющихся descriptions,
  детерминизм и повторная нормализация.
- **HTTP:** общий внутренний harness проверяет фактический статус, обязательные
  headers и их примитивные значения, Content-Type и тело по опубликованной
  response schema. JSON request fixtures успешных сценариев проверяются
  отдельно. Намеренно некорректные запросы проверяются по error response.
  Regression tests описаний сравнивают статусы, headers и байты тела исходной
  и настроенной policy, включая 400, 413 и 415, и проверяют отсутствие вызовов
  функции документации при обработке HTTP-запросов.

Harness использует валидатор с полным документом как корнем ссылок, без
универсального раскрытия JSON Schema. Разрешение OpenAPI Response References
отдельно учитывает локальный `description`, включая пустую строку. Тестовый
resolver раскрывает только чистые schema references, созданные нормализатором;
ресурсные области `$id`, `$defs`, рекурсия и `$ref` с соседними keywords
проверяются отдельно и не подвергаются такому раскрытию.

У test dependency `jsonschema 0.1` обнаружено ограничение: fragment references
внутри вложенного `$id` разрешаются относительно всего документа. Harness
явно отклоняет такие схемы вместо ложного успешного результата. Их встраивание
проверяется структурным сохранением ресурсных областей; рекурсивные ресурсы
дополнительно валидируются отдельно как корневые схемы. Это ограничение тестового
валидатора, а не runtime-валидация или преобразование исходной схемы.

Основной интеграционный тест Petstore проверяет хотя бы один ответ каждой
опубликованной операции. При добавлении endpoint без сценария тест падает.
Runtime-only `/openapi.json` и страницы `/docs` проверяются отдельно.
Встроенные backend conformance tests проверяют адаптеры, в том числе отступы,
значение и Content-Type pretty JSON, а также прежние байты обычной сериализации.
Petstore отдельно проверяет форматирование `/openapi.json`. OpenAPI harness
не подменяет проверки сетевого транспорта и middleware.

Покрытие сценариями и property-based тестами не является доказательством
эквивалентности для всех JSON-значений, всех keywords, диалектов или codecs.
Поддержка примитивных headers в harness не означает поддержку произвольных
стилей сериализации OpenAPI.

## Читаемый OpenAPI

Генератор переиспользует DTO через `components.schemas`, а Response Objects
оставляет внутри операций вместе с исходным описанием, headers и content.
Автоматические `components.responses`, искусственные имена с хешами и режим
Compact отсутствуют. Имена, явно заданные через `schema_name`, сохраняются;
анонимные примитивы и стандартные коллекции остаются inline.

Общие path-параметры поднимаются в Path Item только при полном совпадении у
всех операций этого пути. Query и headers остаются у операций. Тестовый oracle
сравнивает эффективные параметры с учётом наследования и override по `(name, in)`.
Пустой operation description и description, равный summary, считаются
эквивалентными отсутствующему повторению; различающиеся строки сохраняются.
Эта оптимизация не применяется к descriptions ответов и схем.

Локальный `Response.json ~description` имеет приоритет над description DTO,
включая пустую строку. Без override исходное описание сохраняется.
`Decode_error_response.with_description` документирует автоматические ошибки
по статусу; явный ответ того же статуса сохраняет приоритет описания.
В Petstore проверяются описания всех ошибок операций и успешного upload.

Тесты импортированных Response References отдельно сохраняют проверку
локальных description overrides, включая пустую строку. Генератор сам таких
ссылок не создаёт. Совместимость с конкретными внешними инструментами и
генераторами клиентов этим набором не заявляется.

## JavaScript и целые числа

Отдельная команда не входит в `make test` и не требует npm-пакетов:

```sh
make test-js
```

Нужен Node.js с поддержкой `context.source` в reviver `JSON.parse` и
`JSON.rawJSON`. Если возможности отсутствуют, команда завершается понятной
ошибкой. Эти API позволяют восстановить исходный числовой токен как `BigInt`
и сериализовать его числом без промежуточного округления через `Number`.

Вход для JS создаётся настоящими OCaml-кодеками вместе с их схемами.
Проверяются границы `2^53 − 1`, `2^53`, `2^53 + 1`, максимум `int64`
и `max_int` текущей OCaml-платформы:

| Значение | Обычный JS Number |
| --- | --- |
| `2^53 − 1` | Точное safe integer |
| `2^53` | Точное, но уже не safe integer |
| `2^53 + 1` | Теряет точность |
| `2^62 − 1`, OCaml max_int на 64-битной платформе | Теряет точность |

Тесты демонстрируют потерю точности обычного JSON round-trip и точность
lossless round-trip с сохранением числового wire type. Строковый codec с
``[@encoding `string]`` проверяется отдельно и сопровождается схемой
`type: string`: подмена JSON number строкой не соответствует `type: integer`.
Семантика safe integers описана в
[ECMAScript](https://tc39.es/ecma262/multipage/numbers-and-dates.html#sec-number.max_safe_integer).

Это проверка JS JSON-представления, а не совместимости генераторов клиентов.
Генераторы TypeScript, их версии, сетевые запросы и политики lossless-парсинга
пока не входят в набор. Новых runtime-зависимостей у OCaml-пакетов нет.
